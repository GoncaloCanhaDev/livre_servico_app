# Avisos Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** In-app avisos from level 2 and up to the people they reach, cleared with "Visto", private to sender and recipients.

**Architecture:** Two new synced collections (`Aviso`, `AvisoVisto`) with pure helpers in `lib/models/aviso.dart`, an `AvisoService`, a Home card, an Avisos screen and a Novo aviso form; a migration makes the server hide and validate both collections in `pull_records`, the select policy and `push_records`.

**Tech Stack:** Flutter/Dart, Supabase Postgres (PGlite tests).

**Spec:** `docs/superpowers/specs/2026-10-31-avisos-design.md`

## Global Constraints

- Home card: unseen, for this person, sent less than **7 days** ago. Avisos screen: last **30 days**. Text: required, at most **500** characters.
- Senders: level ≥ 2, linked to a person, connected to a store (`StoreAccess.canSendAvisos`). Recipients: people the sender `reaches`, never the sender; teams resolved to person uuids when sent.
- Online ids: `Aviso` by `syncUuid`; `AvisoVisto` by `'<avisoId>/<personId>'` (`syncKey`).
- Dates in JSON as the other models (`dateToJson`), lists of uuids with `stringsFromJson`.
- UI text pt_PT. One commit at the end: `0.69.0+168`, tag `v0.69.0`, CHANGELOG; spec and plan in the same commit.
- Verify with `flutter analyze`, `flutter test`, `npm test` in `supabase/tests`. No APK builds.

## Review Focus

1. A sender who is also picked through a team chip (their own team): must not be a recipient. → Task 1 test.
2. A deleted (tombstoned) aviso: gone from Home and from Recebidos, and its "Visto" rows don't resurrect it. → Task 1 test.
3. An aviso to one person read by another member through a plain `select` or Realtime. → Task 4 test.
4. A pushed aviso naming someone the sender doesn't reach (old app, edited request). → Task 4 test.
5. Someone pushing a "Visto" for another person. → Task 4 test.

**Files:** Create `lib/models/aviso.dart`; Modify `lib/services/local_db.dart` (register `avisos`, `avisoVistos`); Test `test/aviso_test.dart`

**Interfaces (produces):**

- `class AvisoVisto with SyncFields` — `String avisoId`, `String personId`, `DateTime seenAt`; `toJson`/`fromJson`.

- `List<Aviso> avisosOnHome(List<Aviso> avisos, List<AvisoVisto> vistos, String personId, DateTime now)` — not deleted, `toPersonIds` contains `personId`, no visto for (aviso.syncUuid, personId), `sentAt` after `now - 7 days`; newest first.

- `List<String> recipientsFor(StoreAccess access, List<Person> people, {Set<String?> teamIds = const {}, Set<String> personIds = const {}})` — non-deleted people with a `syncUuid`, the account `reaches`, in one of `teamIds` or in `personIds`, not `access.personId`; unique, in `people` order.

### Task 4: Server migration

**Files:** Create `supabase/migrations/20261031230000_avisos.sql`; Test `supabase/tests/sync_schema_test.mjs`

- `aviso_visible(p_store uuid, p_collection text, p_data jsonb) returns boolean` — true for other collections; `Aviso`: admin, sender (`fromPersonId` = my person id), or recipient (`toPersonIds ? my person id`); `AvisoVisto`: admin, `personId` = mine, or I am the sender of `avisoId`'s aviso.
- `records` select policy and `pull_records`: also require `aviso_visible(...)`.
- `push_records`: `Aviso`/`AvisoVisto` leave the bulk insert. New `Aviso`: accepted when `my_level >= 2`, `fromPersonId` is my person, `toPersonIds` non-empty, and every id is a non-deleted Person of the store I `reaches` and not me. Existing `Aviso`: only a delete (deleted_at set) by its sender or the admin. `AvisoVisto`: insert/update only when `personId` is my person and the aviso exists and lists me. The "editors add/change records" policies refuse both collections directly.
- [ ] Tests (end of file, own users/people): sender reads own aviso; recipient reads it; a third member doesn't (pull and plain select); level 1 cannot send; sending to someone not reached is dropped; sender ≠ `fromPersonId` dropped; recipient pushes own Visto, sender reads it, a third member doesn't; pushing a Visto for someone else dropped; a recipient cannot delete; the sender deletes. Run FAIL → implement → PASS.
